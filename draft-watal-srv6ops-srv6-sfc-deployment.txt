               SRv6 Service Function Chaining Deployment
             draft-watal-srv6ops-srv6-sfc-deployment-latest

Abstract

   This document describes the deployment and operational experience of
   the SRv6 Service Function Chaining (SFC) architecture defined in
   [I-D.draft-watal-spring-srv6-sfc-sr-aware-functions] on an academic
   IPv6 backbone network.

   The deployed system integrates SRv6 forwarding, service function
   management, topology collection, path computation, and flow
   classification to enable on-demand provisioning of SFC services via a
   web-based management interface.

   This document summarizes the deployment architecture, operational
   workflow, experience, and lessons learned, and provides guidance for
   operators deploying SRv6 SFC services.

1.  Introduction

   Segment Routing over IPv6 (SRv6) [RFC8986] enables packet steering
   through a set of instructions called a segment list.

   Service Function Chaining (SFC) [RFC7665] can be implemented using
   SRv6 to steer traffic through SR-aware service functions.

   The architecture of SRv6 SFC with SR-aware functions is described in
   [I-D.draft-watal-spring-srv6-sfc-sr-aware-functions].

   This document reports the deployment and operational experience of
   that architecture on an academic IPv6 backbone network.  It does not
   define any new protocols or protocol extensions.

   On-demand provisioning of service function chains requires
   coordination among the forwarding, control, management, and
   application planes.  This document describes how these planes were
   integrated in a multi-site deployment and discusses the operational
   considerations identified through that experience.

3.  Deployment Objectives

   *  Demonstrate the SRv6 SFC architecture on an operational IPv6
      backbone in a geographically distributed, multi-site environment.

   *  Demonstrate incremental deployment without modifying existing
      transit backbone routers.

   *  Evaluate the operational feasibility of on-demand SFC
      provisioning.

   *  Evaluate end-to-end service operation across forwarding, control,
      management, and application planes.

4.1.  IPv6 Backbone

   The deployment was conducted on SINET, Japan's research and education
   network interconnecting universities and research institutions.

   SINET provides native IPv6 connectivity among geographically
   distributed sites.

4.2.  Data Centers

   Three geographically distributed data centers in Hokkaido, Kanagawa,
   and Okinawa were selected to evaluate service chaining over a wide-
   area network.  Each data center provides NFV Infrastructure (NFVI).

4.3.  Video Source Sites

   University-operated video source servers were located at Kanagawa,
   Chiba, Ishikawa, and Okinawa.

4.4.  NFV Infrastructure and Virtualized Infrastructure Manager

   Each data center provides NFV Infrastructure (NFVI) based on
   OpenStack to host SR-aware service functions.  Each site operates an
   independent OpenStack instance as its Virtualized Infrastructure
   Manager (VIM).

5.  Deployment Architecture

   The deployment follows the SRv6 SFC architecture defined in
   [I-D.draft-watal-spring-srv6-sfc-sr-aware-functions].

   The deployed system is organized into four logical planes: the
   forwarding plane, control plane, management plane, and application
   plane.

   The following subsections describe the role of each plane and its
   realization in the deployed system.

5.1.  Overall Architecture

   Figure 2 illustrates the logical architecture of the deployed system.

   *  The application plane provides the operator interface.

   *  The control plane performs topology collection, path computation,
      and SR Policy provisioning.

   *  The management plane deploys and configures service functions.

   *  The forwarding plane forwards traffic through SR-aware service
      functions.

   This architecture enables dynamic deployment and operation of SRv6
   service function chains while preserving the existing forwarding
   infrastructure.

5.2.  Forwarding Plane

   The forwarding plane consists of the existing IPv6 backbone and SR-
   aware service functions deployed at geographically distributed data
   centers.

   Traffic is steered through a sequence of service functions using SRv6
   segment lists.  Each SR-aware service function implements the End.AN
   behavior to process packets and forward them to the next segment in
   the service chain.

   The deployment uses the existing backbone routers without requiring
   SRv6-specific modifications to the transit routers.

5.3.  Control Plane

   The control plane is responsible for topology collection, path
   computation, and SR Policy provisioning.

   A Path Computation Element (PCE) uses a Traffic Engineering Database
   (TED) for topology and resource information.

   A BGP daemon performs two functions:

   *  collecting topology information via BGP-LS, including Service SID
      advertisements

   *  distributing flow classification rules via BGP Flow Specification

5.4.  Management Plane

   The management plane is responsible for deploying, configuring, and
   managing the lifecycle of SR-aware service functions.

   It consists of three logically distinct functions:

   *  Virtualized Network Function Manager (VNFM): defined in [RFC8568],
      responsible for managing the lifecycle of service functions,
      including instantiation, scaling, and termination.

   *  Virtualized Infrastructure Manager (VIM): defined in [RFC8568],
      responsible for managing NFVI compute, storage, and network
      resources.  Each data center has an independent VIM instance,
      while a single VNFM manages all VIM instances across the data
      centers.

   *  Service Function Manager (SFM): defined in
      [I-D.draft-watal-spring-srv6-sfc-sr-aware-functions], responsible
      for configuring SRv6-specific service parameters, including
      Service SID allocation and endpoint behavior, after a service
      function becomes operational (Figure 5).  The allocation procedure
      is described in Section 9.1.

   Each service function instance operates its own BGP-LS speaker (e.g.,
   an embedded agent or sidecar process) and advertises its configured
   Service SID to the control plane after the SFM completes its
   configuration.

   The management plane also supports service function reconfiguration
   and removal throughout their operational lifecycle.

5.5.  Application Plane

   The application plane consists of an operator-facing web-based
   management interface together with the service orchestration logic.
   Based on operator requests, the application plane translates service
   requirements into intent-based service requests and coordinates the
   control and management planes to realize them as deployment
   operations.

   The application plane could be extended with closed-loop automation
   functions that use telemetry feedback from the control and management
   planes.  Such functions could refine service policies and optimize
   service intents based on observed service and network conditions.
   They would operate at a higher level of abstraction and remain
   logically separate from the control and management planes.

6.1.  Service Request

   The operational workflow begins when an operator submits a service
   request through the web-based management interface.

   A service request typically includes:

   *  headend and tailend nodes

   *  optional flow classification rules

   *  the required sequence of service functions

   The application plane translates these service requirements into
   deployment requests for the control and management planes.

6.2.  Network Function Deployment

   If one or more requested service functions are not currently
   available, new service functions are deployed.  Deployment is
   triggered by an explicit operator request.

6.3.  Topology Collection

   Topology information is continuously collected via BGP-LS
   independently of individual service requests.

   After a service function has been instantiated, initialized, and
   verified as operational, the management plane configures its Service
   SID and the corresponding End.AN behavior.

   The service function then advertises its Service SID information via
   the BGP-LS extension defined in
   [I-D.draft-ietf-idr-bgp-ls-sr-service-segments], which is currently
   under standardization.

   Until this advertisement is received, or if the advertisement is
   withdrawn, the service function is not included in the TED and is not
   considered during path computation.

   The SFM is responsible for monitoring the operational state of
   service function instances.  When a service function becomes
   unavailable or is no longer eligible for traffic steering, the SFM
   SHOULD withdraw the corresponding Service SID advertisement via BGP-
   LS.

   Failure to withdraw stale Service SID information may result in
   incorrect path computation.  The same applies if service function
   availability is not reflected in the TED in a timely manner: traffic
   may be steered to non-operational or invalid service functions.

   The control plane maintains the TED based on received BGP-LS
   advertisements and withdrawals.

6.4.  Path Computation

   When a service request is received, the control plane computes an SR
   Policy satisfying the requested service chain based on the current
   network topology and the available service functions stored in the
   TED.

6.5.  SR Policy Provisioning

   As illustrated in Figure 6, the computed SR Policy is provisioned to
   the SR source node acting as the PCC, using PCEP.  The SR Policy
   specifies the SRv6 segment list representing the selected service
   function chain.

6.6.  Flow Classification

   If flow classification is requested, BGP Flow Specification rules are
   installed, as shown in Figure 6, associating each traffic flow with
   its SR Policy by Color, to ensure that only the selected traffic
   flows traverse the deployed service function chain.  Installation
   ordering relative to SR Policy provisioning is discussed in
   Section 9.4.

6.7.  Traffic Steering

   Once the SR Policy and Flow Specification rules shown in Figure 6 are
   installed, the SR source node begins steering matching traffic
   through the selected service functions.

6.8.  Monitoring

   Operational status is continuously monitored throughout the service
   lifecycle using telemetry collected from both the network and
   infrastructure.

   Operators may also verify traffic steering using SR path tracing or
   in-band telemetry mechanisms.

   For content-modifying services, application-layer verification may be
   required in addition to network and infrastructure monitoring, as
   discussed in Sections 8.1 and 9.3.

6.9.  Service Update and Removal

   The deployed system supports updates throughout the service
   lifecycle.

   Typical operations include:

   *  modifying service function chains

   *  removing service function chains

   *  redeploying failed service functions

   *  removing service functions

   Service updates require coordination among the forwarding, control,
   management, and application planes to maintain operational
   consistency.

   The ordering and verification of update operations are discussed in
   Section 9.4.

7.  Deployment Experience

   This section describes the deployment and operational experience of
   the SRv6 SFC architecture.

   The deployed system supported a remote video production service.

   The following subsections describe the deployed architecture, the
   deployed service, and the resulting operational observations.

7.1.  Deployed System Architecture

   The deployment used the environment described in Section 4.

   The deployed system implements the following components:

   *  Application plane: a web-based management interface and service
      orchestration component.

   *  Control plane: Pola PCE for path computation and SR Policy
      provisioning, together with GoBGP for BGP-LS topology collection
      and BGP Flow Specification distribution.

   *  Management plane: a VNFM, OpenStack as the VIM, and Ansible as the
      SFM.

   *  Forwarding plane: the existing backbone and distributed SR-aware
      service functions.

7.2.  Service Deployment

   Video streams from the video source sites described in Section 4.3
   were dynamically steered through SR-aware service functions deployed
   in the Hokkaido, Kanagawa, and Okinawa data centers.

   The service functions performed video switching, transcoding, color
   correction, and caption insertion before forwarding the processed
   streams to the production system.

   Operators created service function chains through the web-based
   management interface.

   The management plane instantiated the distributed service functions,
   after which Service SIDs were assigned and the corresponding
   information was advertised via BGP-LS.

7.3.  Operational Benefits

   The deployed system demonstrated several operational benefits.

   *  No modifications to the existing backbone infrastructure were
      required for deployment or operation.

   *  Service functions were deployed on demand using the existing NFV
      infrastructure.

   *  SR Policies and Flow Specification rules were automatically
      generated.

   *  Operators manage services through an intent-based interface,
      without requiring awareness of low-level network details, thereby
      reducing operational complexity.

7.4.  Scalability Considerations

   This deployment demonstrated that additional SR-aware service
   functions can be introduced without changing the overall control
   architecture.

   Once instantiated, configured, and advertised via BGP-LS, these
   service functions become available for path computation without
   requiring manual updates to the controller configuration.

8.  Lessons Learned

   This section describes observed operational behaviors.  It does not
   specify requirements or recommendations.

   During the deployment of the SRv6 SFC system on the backbone, several
   operational issues and design insights were identified.  This section
   summarizes key observations obtained from real-world operation.

8.1.  Service Verification and Observability

   Verifying end-to-end service correctness requires more than
   monitoring SR Policy status or the operational state of service
   functions.

   For the deployed video processing service, network-layer monitoring
   alone was insufficient to verify the correctness of the processing
   results.  Application-layer verification was needed to compare input
   and output video streams.

   For service chains consisting of multiple content-modifying service
   functions, checking only the original source and final destination
   was insufficient to identify which service function caused an
   incorrect processing result.

   This experience demonstrated the need for application-layer
   verification as a complement to network- and infrastructure-layer
   monitoring.

8.2.  Multi-domain State Correlation Limitations

   The deployed system spans multiple VIM domains distributed across
   geographically separated data centers.

   Operational state is distributed across network, infrastructure, and
   application layers, each monitored using independent tools.
   Consequently, no unified mechanism was available to correlate SR
   Policy state, service function status, and application-layer
   verification results.

   Troubleshooting therefore required manual correlation of information
   from multiple sources.

   This lack of unified state correlation increased the effort required
   to identify the source of service failures across the network,
   infrastructure, and application domains.

8.3.  Service Orchestration Timing and Consistency Issues

   Correct service operation depends on the ordering and timing of
   service function readiness, Service SID advertisement, SR Policy
   provisioning, and Flow Specification installation.

   Delays in BGP-LS propagation and TED synchronization may cause
   discrepancies between the actual service function state and the state
   used for path computation.

   Similarly, installing Flow Specification rules before the
   corresponding SR Policy becomes operational may result in transient
   traffic misclassification or blackholing.

   These observations motivate the operational sequencing
   recommendations described in Section 9.4.

9.  Operational Considerations

   SRv6 SFC deployments require coordination among the control,
   management, and application planes to ensure consistent service
   operations.

9.1.  Service SID Allocation

   Service SID allocation MUST ensure that distinct service functions
   within the same Locator do not inadvertently use the same Function
   value.

   When multiple service function instances are intentionally configured
   to share an Anycast Service SID, the shared SID MUST be treated as a
   single logical service endpoint.  Such sharing MUST be explicitly
   coordinated to ensure that all instances provide compatible service
   behavior.

   Reachability to the node hosting a service function is provided by
   the SRv6 Locator assigned to that node and advertised through normal
   IGP/BGP routing.  Transit nodes along the path only need to maintain
   reachability to this Locator; they are not required to be aware of
   the Service SIDs corresponding to individual service functions
   providing the End.AN behavior.

   In this deployment, the SFM checked which Function values were
   already in use and selected an available value before configuring the
   corresponding End.AN behavior.

   This approach reduces the risk of collisions with already allocated
   Service SIDs and provides a consistent allocation procedure across
   the distributed data centers.

9.2.  Failure Recovery

   Failure recovery follows the mechanisms defined in
   [I-D.draft-watal-spring-srv6-sfc-sr-aware-functions].

   In operational deployments, fast reroute at the forwarding plane can
   maintain network connectivity, but it does not necessarily guarantee
   service-level state consistency.

   During failover, traffic may be redirected to a different service
   function instance that does not share the processing state of the
   original instance.

   Service-level recovery may require application-specific mechanisms to
   handle state inconsistencies when traffic is redirected to a
   different service function instance.  The appropriate mechanisms
   depend on the service function and its processing model.

9.3.  Observability

   Effective observability for SRv6 SFC involves monitoring multiple
   aspects of the system, including:

   *  SRv6 topology and SR Policy state

   *  Flow classification and traffic steering behavior

   *  Service function health and availability

   *  Virtual infrastructure resource utilization

   *  Application-level service processing results

   The deployment did not provide a unified telemetry system spanning
   the network, NFV, and application domains.  Correlating operational
   state across these domains therefore required manual investigation.
   A unified telemetry system could help correlate events and support
   fault detection and diagnosis.

   For content-modifying services, application-layer verification SHOULD
   include mechanisms to compare the input and output of individual
   service functions.

   Packet mirroring capabilities at SRv6 endpoints may provide
   additional information for service-level monitoring and
   troubleshooting.  The applicability of such capabilities to SRv6 SFC
   deployments requires further investigation.

9.4.  Operational Sequencing

   Automated orchestration SHOULD ensure that service functions are
   instantiated, configured, and verified as ready before their Service
   SIDs are advertised via BGP-LS.

   The corresponding SR Policy SHOULD be provisioned and verified before
   Flow Specification rules are installed to steer traffic through the
   service chain.

   When an existing SR Policy is modified or replaced, flow
   classification rules SHOULD be updated only after the replacement
   policy has been successfully provisioned and verified.

   These procedures help avoid transient traffic misclassification and
   blackholing during service deployment and updates.

10.  Security Considerations

   The security considerations in [RFC8402], [RFC8986], and [RFC9256]
   apply to this deployment, which relies on the SR domain trust model
   described in [RFC8402].  Operators MUST ensure that SRv6 packets
   originating outside the trusted SR domain are not processed as SRv6
   traffic at domain boundaries.

   This deployment provisions SR Policies to SR source nodes directly
   via PCEP, consistent with the PCE-initiated LSP model described in
   [RFC8231] and [RFC8281].  Without adequate protection, an attacker
   could inject or modify PCEP messages to provision unauthorized SR
   Policies.  Operators SHOULD ensure that PCEP sessions used for SR
   Policy provisioning are protected using appropriate authentication,
   authorization, and integrity protection mechanisms.

   Because service functions are instantiated dynamically and become
   eligible for path computation after Service SID advertisement (see
   Section 6.3), operators SHOULD ensure that Service SID information is
   advertised only for authenticated and authorized service functions.

   The management plane SHOULD verify the identity and integrity of a
   service function instance before advertising its Service SID into the
   SR domain.  If this verification is not performed, a rogue or
   compromised service function could be selected during path
   computation, resulting in traffic being steered to an unauthorized
   function.

   Operators SHOULD ensure that topology and Service SID information
   advertised via BGP-LS is protected against unauthorized modification
   or injection.

   Operators SHOULD ensure that BGP-LS topology and Service SID
   information is distributed only to authorized consumers.

   Management interfaces SHOULD be protected using mutually
   authenticated secure transport protocols.

   Operators SHOULD ensure that flow classification rules and Color
   values used to associate them with SR Policies are protected against
   unauthorized modification or injection using appropriate
   authentication, authorization, and integrity protection mechanisms.

   Unauthorized modification or compromise of flow classification rules,
   Color values, or SR Policies may result in unintended traffic
   steering, service misbehavior, or service disruption.
